# 微信 AI 聊天助手

Windows 上的本地回复草稿工具：读你**当前打开的那一屏**微信对话，按你的说话习惯
生成三条可以直接发出去的回复，显示在自己的小窗口里 —— 复制、粘贴、发送全部由你手动完成。

- **下载（Windows 10/11 64 位）**：[GitHub Releases](https://github.com/zzzzzzzzyl/wechat-ai-assistant/releases)
  → `wechat-ai-assistant-win64.zip`（约 105 MB，解压后 248 MB，不需要装 Python）
- **介绍页**：[zzzyl.xyz/projects/wxai](https://zzzyl.xyz/projects/wxai/)

**它不做什么**（这是这个项目的红线，也是它和"外挂"的区别）：

- ❌ 不模拟键鼠、不点击微信、不自动复制粘贴、**不自动发送任何消息**
- ❌ 不读写微信数据库、不注入进程、不 hook 网络、不破解加密

通过 UIA 树或者 OCR **只读**微信窗口已经显示出来的内容，本地存储后提供上下文支持。

下面的内容分三章：**一、怎么拿到数据**（两条读取链路）· **二、数据存在哪** ·
**三、怎么交给智能体**。

# 一、微信聊天记录获取

## 1.1 项目边界

本项目是**本地学习研究**用途，全部代码**只读**：

- ✅ 读取微信窗口已显示的聊天内容、会话列表
- ✅ 监听/统计消息变化
- ✅ 生成 AI 推荐回复并显示在独立窗口
- ❌ **不模拟键鼠、不点击微信、不自动复制粘贴、不自动发送任何消息**
- ❌ 不读写微信数据库文件、不注入进程、不 hook 网络

复制、粘贴、发送全部由用户手动完成。任何后续功能都不得越过这条线。

## 1.2 结论速览：**两条读取链路并存**

| | **UIA 链路** | **OCR 链路** |
|---|---|---|
| 怎么读 | 读微信的 UI Automation 控件树 | `PrintWindow` 抓整窗 → 定几何 → 切行 → 逐行 OCR |
| 什么时候能用 | 微信**暴露控件树**的环境 | **拿不到控件树**的环境 |
| 精度 | 文本零误差、结构化 | 可能识别错字（有语料验收台把关） |
| 后台 | **最小化 / 隐藏也能读** | 不怕遮挡，**但最小化抓不到** |
| 速度 | 一屏 **50~90 ms** | 探针 **34 ms**；真变了一屏 ≈ **380 ms** |

⚠️ **不是"主力 + 兜底"**：**大部分环境拿不到 UIA 树，只有部分账号 / 机器能拿到**
（见 1.4），所以两条链路**都是常态路径**，由 `reader.backend: auto` **自动选路**
（能拿到控件树走 UIA，拿不到整屏走 OCR，选中后不再来回切）。
两条都**不是"半条"**：各自都能独立读完整一屏，输出**同一种 `ChatSnapshot`**，
下游（发送者判定、存储、提示词）**不需要知道这次是谁读的**。

## 1.3 UIA 链路

### 1.3.1 能力清单

微信 4.1.13.65 是 **Qt 5.15.14** 应用（主窗口类名 `Qt51514QWindowIcon`）。
⚠️ 网上绝大多数「UIA 抓微信聊天记录」教程针对的是 **3.9 的 `WeChatMainWndForPC`**，
在 4.x 上直接失效；本节的控件类名（`mmui::*`）只适用于 4.x。

> ⚠️⚠️ **取法比什么都重要**：逐级遍历（`GetChildren()` 递归）在微信主窗口上只能拿到
> **78 个元素**，消息列表和会话列表底下**空无一物** —— 看上去就像"微信不暴露消息"。
> 换成一次性查全部后代（`FindAll(TreeScope_Descendants)`）**同一个窗口变成 160~170 个元素**，
> 消息文本、会话项、输入框全在。原因是 Qt 的 provider 给自绘虚拟列表实现了 `FindAll`、
> 没实现 walker 遍历。**所以下面这些"能拿到"都以此为前提。**

| 内容 | 控件类 / AutomationId |
|---|---|
| 当前聊天标题 | `mmui::XTextView`，id 含 `current_chat_name_label` |
| 消息列表容器 | `mmui::RecyclerListView`，id = `chat_message_list` |
| 消息条目 | `mmui::ChatTextItemView`（文本）/ `ChatBubbleReferItemView`（图片·表情·引用）/ `ChatBubbleItemView`（文件·视频），Name = 消息正文 |
| 会话列表项 | `mmui::ChatSessionCell`，id = `session_item_<会话名>`，Name = 「会话名\n预览\n时间」 |
| 输入框 | `mmui::ChatInputField`，id = `chat_input_field`（可用 ValuePattern 读内容） |

**能稳定拿到**（实测样例里的会话名/昵称都换成了占位名）：

| 信息 | 来源 | 样例 |
|---|---|---|
| 会话列表（标题/预览/时间） | `ChatSessionCell` 的 Name（`\n` 分段） | `张三` / `好了` / `00:58` |
| 会话免打扰标记 | 同上，Name 末段为 `消息免打扰` | `示例24新生群` |
| 当前聊天标题 | `current_chat_name_label` | `张三` |
| 消息正文 | 消息项 Name | `猪猪`、`好了` |
| 消息类型 | 消息项控件类 | 文本 / 图片·表情·引用 / 文件·视频 |
| 消息行位置与高度 | 消息项 `BoundingRectangle` | 高度 `[228, 153, 84, 84]` |
| 输入框内容 | `chat_input_field` + **ValuePattern** | 你此刻正在输入的字 |
| 导航栏与按钮 | `mmui::XTabBarItem` / `mmui::XButton` | `聊天记录`、`截图(Alt+A)`、`发送文件` |

**拿不到（已逐条验证）**：

| 信息 | 原因 |
|---|---|
| 消息是对方还是自己发的 | 消息项 rect 是**整行**；`ItemStatus/ItemType/HelpText/AriaRole` 全空；**不支持 TextPattern** → 只能看像素（见 1.3.3） |
| 未读消息**条数** | `mmui::XBadge` 元素存在（导航栏 4 个，各 25×25），但**不含数字**，只能靠会话预览变化推断 |
| 消息级时间戳 | 消息项 Name 里没有时间；只有会话列表有时间 |
| 历史消息 | `RecyclerListView` 是虚拟列表，只返回已渲染的可见项（见 1.3.5） |
| 群聊昵称 | 群聊消息项的子元素是 0 个，全窗口 `TextControl` 只有 5 个（群名/成员数/群描述…），**没有昵称** → 只能 OCR（见 1.3.4） |
| 图片 / 表情的实际内容 | 只有 `[图片]`、`[动画表情]` 占位文本 |

**最强的一点**：窗口**最小化**甚至 `SW_HIDE` 完全隐藏时，UIA 依然能读到全部内容 ——
实测三种状态下（被遮挡 / 最小化 / 隐藏）都是 **同样的 4 条消息、9 个会话、159~160 个元素**。
→ UIA 与窗口显示状态**无关**，可实现真正的后台常驻，用户无需保持微信窗口可见。

### 1.3.2 性能

```
耗时: 最小 28 ms / 平均 40 ms / 最大 80 ms
元素 159 个，无随轮次上升的性能退化 => 无泄漏，可长期运行
期间成功捕捉到内容指纹变化与会话切换 => 可用于新消息检测
```

单次完整读取约 **40 ms**，轮询间隔 1 秒余量极大。（对比：OCR 链路见 1.4.2 ——
它的**探针**只要 34 ms，但真读一屏约 380 ms。）

### 1.3.3 发送者区分

UIA 给每行精确 rect → 用 `PrintWindow(PW_RENDERFULLCONTENT=2)` 把**整窗抓成位图**
（⚠️ **不需要把微信置顶、不需要它在前台**：实测聊天区被浏览器和悬浮窗同时盖住时，
它抓到的内容和 UIA 读到的文本 **5/5 完全对上**；同一时刻屏幕截图的命中率是 **0/5**，
而且 OCR 出来的是别的窗口的文字）→ 按行裁图 → 用该行左右边缘估计背景色 →
找出与背景差异大的「内容像素」（头像/气泡）→ 统计其在行内左半 / 右半的分布。

| 消息 | 左半占比 | 判定 |
|---|---|---|
| 谢谢你们 | 1.00 | 对方 |
| 示例消息三 | 1.00 | 对方 |
| 示例消息四 | 0.00 | 自己 |
| 示例消息二 | 1.00 | 对方 |

阈值取 0.75 / 0.25 余量充足。**绿色气泡**（自己发的是绿色）只作**兜底**判据
（绿像素占比 > 3%），因为实测**对方头像里也稳定含绿色像素**，不能当唯一判据。
唯一仍会失败的情况是窗口**最小化**（那时 `PrintWindow` 只拿到空白，用 `is_blank()` 拦掉，
本次不判定、`is_self` 留"未知"，不猜）。

### 1.3.4 群聊 —— UIA 没有昵称，必须靠 OCR 分辨是谁

单聊靠像素只能分「左=对方 / 右=自己」；但群聊左侧可能同时有多个人，必须知道**是谁**。
实测 UIA 树里根本不存在昵称，昵称只能靠 OCR。两条实测规律：

1. 有昵称的行高 **115**，没有昵称的行高 **84** —— 也就是微信在别人的消息上方多画了一行昵称。
2. **昵称固定在行内左上**（x≈104, y≈15），正文在其下方（x≈122, y≈61）。

→ **群聊最终方案：UIA 取正文（精确）+ 行高判断有无昵称 + OCR 取昵称 + 像素判左右。**
昵称判定的三条判据（行高 / 位置 / 同一个名字要**在不同拍里复现两次**才认）见 1.4.4。

### 1.3.5 已知的两个坑

- ⚠️ **定位窗口**用 `win32gui.EnumWindows` 拿 HWND，**禁止** `GetRootControl().GetChildren()`
  —— 实测后者在本机 **60 秒不返回**（机器上同时有 11 个 `WeChatAppEx.exe` 小程序运行时，
  某个 provider 无响应就把全量枚举拖死）。
- ⚠️ 微信会同时开好几个**同类窗口**（主窗口 / 「图片和视频」预览 / 朋友圈 / 设置），
  而 `EnumWindows` 的返回顺序**不保证**（实测同机两次就不同）。挑中「图片和视频」
  预览时就**什么都读不到**，和"微信改版了 / UIA 坏了"完全分不开。
  **唯一可靠的纯 Win32 判据是标题**（主窗口恒为「微信」）：只认标题**精确等于**
  「微信」的那个，分不出来就返回 `None`（宁可不读也不瞎读）。

## 1.4 OCR 链路

最开始我在本机测试时 UIA 是可以拿到内容的，但打包到其他设备、用不同账号测试后发现：
微信只把 **2 个后代控件**（`MMUIRenderSubWindowHW` + `Qt51514QWindowIcon`）暴露给
UI Automation，于是**什么都读不到**（不报错、不崩，就是空的）。

而**从实际反馈看：拿不到控件树的是大多数环境，能拿到的只有部分账号 / 机器**。
根因**不在客户端可控范围**：账号级的 `config` / `resource` / `db_storage` 整体置换之后
树仍然是空的，剩下的是「服务器按设备 + 账号下发」。我就不跟微信在这件事上纠缠了，
**直接自己加了 OCR 这条路**。

| | |
|---|---|
| 判据 | 数后代控件：正常 **160~170**、拿不到 **2**，门槛 **20**（一次全量 `FindAll`，约 50 ms） |
| 挂在哪个函数 | **`read_chat_title`**，不是 `read_chat`（记录器是"标题为空就整拍跳过"，挂后者等于没做） |
| 选路之后 | **不再来回切**（想重试就重启）：来回试只会让每拍多花一次抓图 + OCR |

### 1.4.1 能力清单

**能拿到**（和 UIA 对齐：同一批字段、同一种 `ChatSnapshot`）：

| 信息 | 怎么来的 |
|---|---|
| 当前聊天标题 | 标题栏区域 OCR + 按位图宽度自己检测左边界 |
| 消息正文 | 按**气泡连通域**切出行 → 逐行 OCR |
| 消息类型 | 气泡几何 + 文字与图标：文本 / 图片 / 引用 / **文件** / **链接** / **系统提示**（六类） |
| 发送者左右 | 气泡在行内靠左还是靠右（**和 UIA 共用同一套 `sender.py`**） |
| 群聊昵称 | 行内左上角 OCR（判据见 1.4.4） |
| 时间分隔符 | 居中的灰色小字（"昨天 22:22"那一类） |

**拿不到**（与 UIA 的差别，也是它的**三个已知损失**）：

1. **上下文只有当前一屏** —— 想读更多就得替你滚动微信，那是模拟输入、**踩红线**。
   （替代方案是本地把每屏存下来缝合，见第二章。）
2. **不提供会话列表和输入框内容**（`read_sessions` 返回 `[]`、`read_input_text` 返回 `""`）。
3. **图片 / 表情分不出来**（OCR 只认字）—— 不过它的**气泡分类**反而比 UIA 细：
   引用块、分享卡片、系统提示都能按形状认出来。

### 1.4.2 性能与优化（从"一张 9 秒"到能常驻）

| 环节 | 之前 | 现在 | 怎么做到的 |
|---|---|---|---|
| 单张 OCR | **9.19 s**，还把 20 个核拉满 | **0.13 s** | ① `intra_op_num_threads=4`（线程数"自动"在识别模型上要 **233 ms**，显式 4 线程只要 **12 ms**）；② `limit_type: max`（`min` 的语义是"短边 ≥ 736"，会把一条 978×84 的消息行放大成 736×2944，**面积 26 倍**）；③ `use_cls=false` |
| 每拍开销 | 每拍真读一屏 ≈ **380 ms** | **探针 34 ms** + 变了才真读 | 探针 = 抓图 + 缩略图哈希、**不做 OCR**，只覆盖「标题栏 + 聊天区」（免得你自己打字就触发一次真读）。⚠️ **探针里绝不能有像素分析**（第一版 132 ms，比 UIA 还贵） |
| 引擎加载 | 每次冷启动 1~3 s | 只加载一次（懒建） | 第一次真读时才建引擎，之后常驻；空闲时零 OCR |
| 质量把关 | 靠肉眼 | **本地语料验收台** | 11 张人工核对的 golden 对 23 张真机语料：召回从旧版的 **30.8% 拉到 100%**（语料是真实聊天截图，**不随仓库分发**，用法见 `tests/corpus/README.md`） |

### 1.4.3 切行与几何：**检测优先，配置兜底**

- 「导航栏 + 会话列表」的宽度**不是常数**：1542 宽的窗口分界 **465**、1206 宽是 **430** ——
  写死配置值（465）在窄窗口上会**偏右 35 像素**，够吃掉标题第一个字。
  所以：**自己检测优先**（按位图宽度缓存），认不出来才用配置兜底。
- 安全性靠两条：① 检测**认不出来就返回 `None`**；② 认出来的值**还得真能认出气泡**才算数。
- ⚠️ 判定"两块颜色是不是同一片"的容差**别调大**：聊天区与会话列表的色差只有 28~51，
  容差放到 60 就会把两边判成同色。底色**要取众数**，别拿最右几列平均（那儿常是滚动条）。
- ⚠️ 几何不对时**要说出来**，不能和"没打开会话"长成一个样（日志里会点名几何异常）。

### 1.4.4 群聊昵称（三条判据 + 复现两次）

| 判据 | 值 |
|---|---|
| 行高 | 有昵称 **115** / 没有昵称 **84** |
| 位置 | 昵称固定在行内**左上**（x≈104, y≈15），正文在其下方（x≈122, y≈61） |
| 确认 | 同一个名字要在**不同的拍里复现两次**才认（OCR 会偶发读错字） |

⚠️ 认不出来的写「**群友**」而不是「对方」——「对方」在中文里暗示"只有两个人"，
群里会把多个人看成同一个；**私聊里则绝不出现「群友」**（一个昵称都没认出来 = 没有证据，
保持「对方」）。长昵称 / emoji 昵称 / @提及 / 群成员改名片这些样本还不够，
**这是目前最不稳的一环**。

## 1.5 两条链路的取舍

| 维度 | UIA 链路（有控件树的环境） | OCR 链路（拿不到控件树的环境） |
|---|---|---|
| 消息文本 | 精确、零误差 | 可能识别错字 |
| 会话列表（预览/时间） | 结构化 | 不提供 |
| 消息类型 | 靠控件类区分（文本/图片/引用/文件/链接/系统提示） | 靠气泡几何 + 文字与图标，也一样分这六类（**按各自气泡特征分类，比较麻烦**） |
| 抗遮挡 / 后台 | **完全不受影响**，最小化 / 隐藏都能读 | `PrintWindow` 不怕遮挡，**但最小化就抓不到** |
| 发送者左右区分 | 单靠自己拿不到 → 配合同一次抓图的像素 | 气泡像素坐标直接判左右（**同一套 `sender.py`**） |
| 图片消息内文字 | 只有 `[图片]` 占位 | 可识别 |
| 群聊发送者昵称 | 没有 → 也要靠 OCR（见 1.3.4） | OCR 读行内昵称（见 1.4.4） |
| 速度 | 一屏 **50~90 ms** | 探针 **34 ms**；真读 ≈ **380 ms** |
| 选路 | `auto` 自动选；选中后**不来回切** | 同左 |

⚠️ **不做逐条混用**（比如"UIA 取正文 + OCR 只补昵称"当主路径）：两边坐标系和切行方式
都不一样，混着用等于每拍两次取图 + 一次 OCR。昵称那种"补一点"的用法只出现在
**同一条链路内部**。

# 二、内容存储

屏幕是**虚拟列表**，往上滚就换一批 —— 所以"上下文"必须自己攒。两个本地 SQLite 库，
分工不同：

| 库 | 管什么 | 容量 |
|---|---|---|
| `screens.db`（屏快照） | **上下文的顺序**：每拍把"这一屏长什么样"整体存一条，靠**重叠点**把相邻屏缝起来 | 每个会话最近 **40 屏** |
| `history.db`（消息表） | **一条条消息**：口吻样本、AI 自我污染标记、清空 | 每个会话最近 **500 条** |

- ⚠️ 两者都**不是存档**，只是"最近上下文的窗口"，超了自动淘汰。
- ⚠️ 判不出"**在不在底部**"时**宁可不写**：把"往上翻历史"误当成"新消息"会让库里
  一秒写进 26 条别的窗口的画面（实测踩过）。
- ⚠️ 写库前有**三道闸**：① 垃圾标题（`X` / `+` / `①` 这类 OCR 碎片）连正文都不读；
  ② 只给**确认过的会话**写库（同一个标题要在不同拍里出现两次）；③ 切会话的那一拍
  要"**读完正文再读一次标题**"，两次指向同一个会话才放行（否则会把新消息记到旧会话名下）。
- ⚠️ **会话键是标题原文** → 重名的会话会串（目前只合并了 emoji 变体）。

数据全部在本地，程序**不往任何服务器上传**（除了你自己配的 AI 接口，见第三章）。

# 三、提交给智能体

## 3.1 回复目标 = **当前屏幕的整段对话**

不是"最后一条"：屏幕上那几条**都是**回复目标，提示词里明确写了
「最后一条是最新的，前面几条是刚发生的背景」。这样模型不会只盯着最后一句答非所问。

## 3.2 上下文的三道闸

| 闸 | 默认值 | 为什么 |
|---|---|---|
| 条数 | **20 条** | 再多也没人看 |
| 单条长度 | **500 字/条** | ⚠️ 只限条数防不住长内容：实测粘一条 2000 字的提示词，就把上下文从 57 字撑到 2071 字、**每次贵 3 倍**，而"20 条以内"对它完全无感 |
| 总长度 | **4000 字**（超了**从最旧丢**） | 兜住上面两条之外的极端情况 |

回复目标那几条会**从历史里摘掉**，否则同一段话在提示词里出现两次。

## 3.3 提示词是怎么拼出来的

```
{人设}                    ← 设置里的「人设」
{关系} + {口吻样本}        ← 关系描述 + 你平时说话的样本
{我想说}                  ← 只在填了的时候拼，且是【最高优先级】
<你那一框>                 ← 【硬性禁止】+【上下文规则】（自己可改）
【输出要求】               ← 代码侧，含"生成几条"
```

- **「我想说」**那一栏填了就用它压过模型的立场推断，**用完即清**（那句话是"这一次"的意思）。
- **口吻样本必须排除 AI 生成过的消息**：AI 建议 → 你发出去 → 进库 → 下一轮被当成
  "我平时说话的样子" → AI 开始模仿自己，几轮下来 AI 腔越来越重。库里给每条 AI 建议
  打了标记，取样时跳过（但它**仍然算对话历史** —— 那确实是你发出去的真实消息）。
- 出厂时**接口地址 / 模型 / Key 都是空的**：本程序不替你选服务商
  （预填等于替你选了，换一家时只填 Key 会静默打到原来那家）。三样齐全才会真发请求，
  缺哪样状态行会点名；设置里的【测试连接】会发一次最小请求告诉你行不行。

## 3.4 钱花在哪（实测）

- ⚠️ **模型的"思考"也计费**：实测一次生成输出 680 token 里 **540 是思考**，
  而输出的单价是输入的 **4 倍** —— **想省钱，大头在思考上，不在压缩提示词**。
- 输出的结构由代码侧的【输出要求】约束，解析（`parse_replies`）依赖它，
  所以在设置里改不到它、也就改不坏。

# 四、已知限制与后续

1. **历史消息不做，也不打算做**：消息容器是虚拟列表，想读更多就得**替你滚动微信**，
   那是模拟输入、踩红线。替代方案是上面那两个库 + 重叠点缝合。
2. **群聊昵称仍然不稳**：样本只有几个群，长昵称 / emoji 昵称 / @提及还没测全（见 1.4.4）。
3. **图片 / 表情的内容看不到**：UIA 侧只有 `[图片]` 占位；图片里的文字是否值得 OCR
   还在调研，目前没做。
4. **只有 Windows + PC 微信 4.x**：微信一升级，控件类名可能要跟着改
   （都集中在 `config.yaml` 里，改一处即可）。
5. 打包与分发：`build_exe.bat` → `make_zip.py` → `verify_zip.py` 一条链；
   体积构成与瘦身记录不在本文件里。
