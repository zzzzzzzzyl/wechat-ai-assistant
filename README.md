# 一、微信记录获取

## 1.1 项目边界

本项目是**本地学习研究**用途，没有对微信进行任何自动化操作：

- ✅ 读取微信窗口已显示的聊天内容、会话列表
- ✅ 监听/统计消息变化
- ✅ 生成 AI 推荐回复并显示在独立窗口
- ❌ **不模拟键鼠、不点击微信、不自动复制粘贴、不自动发送任何消息**
- ❌ 不读写微信数据库文件、不注入进程、不 hook 网络

**复制、粘贴、发送全部由用户手动完成。任何后续功能都不得越过这条线。**

## 1.2 结论速览：**两条读取链路并存**

| | **UIA 链路** | **OCR 链路** |
|---|---|---|
| 怎么读 | 读微信的 UI Automation 控件树 | `PrintWindow` 抓整窗 → 定几何 → 切行 → 逐行 OCR |
| 什么时候能用 | 微信**暴露控件树**的环境 | **拿不到控件树**的环境 |
| 精度 | 文本零误差、结构化 | 可能识别错字（有语料验收台把关） |
| 后台 | **最小化 / 隐藏也能读** | 不怕遮挡，**但最小化抓不到** |
| 速度 | 一屏 **50~90 ms** | 探针 **34 ms**；真变了一屏 ≈ **380 ms** |

## 1.3 UIA 链路

### 1.3.1 能力清单

微信 4.1.13.65 是 **Qt 5.15.14** 应用（主窗口类名 `Qt51514QWindowIcon`）。
网上绝大多数「UIA 抓微信聊天记录」教程针对的是 **3.9 的 `WeChatMainWndForPC`**，在 4.x 上直接失效。

| 内容 | 控件类 / AutomationId |
|---|---|
| 当前聊天标题 | `mmui::XTextView`，id 含 `current_chat_name_label` |
| 消息列表容器 | `mmui::RecyclerListView`，id = `chat_message_list` |
| 消息条目 | `mmui::ChatTextItemView`（文本）/ `ChatBubbleReferItemView`（图片·表情·引用）/ `ChatBubbleItemView`（文件·视频），Name = 消息正文 |
| 会话列表项 | `mmui::ChatSessionCell`，id = `session_item_<会话名>`，Name = 「会话名\n预览\n时间」 |
| 输入框 | `mmui::ChatInputField`，id = `chat_input_field`（可用 ValuePattern 读内容） |

**能稳定拿到**（实测样例里的会话名/昵称都换成了占位名）：

| 信息 | 来源 |
|---|---|
| 会话列表（标题/预览/时间） | `ChatSessionCell` 的 Name（`\n` 分段） |
| 会话免打扰标记 | 同上，Name 末段为 `消息免打扰` |
| 当前聊天标题 | `current_chat_name_label               |
| 消息正文 | 消息项 Name |
| 消息类型 | 消息项控件类 |
| 消息行位置与高度 | 消息项 `BoundingRectangle              |
| 输入框内容 | `chat_input_field` + **ValuePattern** |
| 导航栏与按钮 | `mmui::XTabBarItem` / `mmui::XButton   |

**拿不到（已逐条验证）**：

| 信息 | 原因 |
|---|---|
| 消息是对方还是自己发的 | 消息项 rect 是**整行**；`ItemStatus/ItemType/HelpText/AriaRole` 全空；**不支持 TextPattern** → 只能看像素（见 1.3.3） |
| 未读消息**条数** | `mmui::XBadge` 元素存在（导航栏 4 个，各 25×25），但**不含数字**，只能靠会话预览变化推断 |
| 消息级时间戳 | 消息项 Name 里没有时间；只有会话列表有时间 |
| 历史消息 | `RecyclerListView` 是虚拟列表，只返回已渲染的可见项（见 1.3.5） |
| 群聊昵称 | 群聊消息项的子元素是 0 个，全窗口 `TextControl` 只有 5 个（群名/成员数/群描述…），**没有昵称** → 只能 OCR（见 1.3.4） |
| 图片 / 表情的实际内容 | 只有 `[图片]`、`[动画表情]` 占位文本 |

**最强的一点**：窗口最小化甚至 `SW_HIDE` 完全隐藏时，UIA 依然能读到全部内容。
→ UIA 与窗口显示状态**无关**，可实现真正的后台常驻，用户无需保持微信窗口可见。

### 1.3.2 性能

```
耗时: 最小 28 ms / 平均 40 ms / 最大 80 ms
元素 159 个，无随轮次上升的性能退化 => 无泄漏，可长期运行
期间成功捕捉到内容指纹变化与会话切换 => 可用于新消息检测
```

### 1.3.3 发送者区分

UIA 给每行精确 rect → 用 `PrintWindow` 把整窗抓成位图→ 按行裁图 → 用该行左右边缘估计背景色→找出与背景差异大的（头像/气泡）→ 统计其在行内左半 / 右半的分布。

阈值取 0.75 / 0.25 余量充足。也可以通过判断绿色气泡只作兜底判据。

唯一仍会失败的情况是窗口最小化，那时 `PrintWindow` 只拿到空白。

### 1.3.4 群聊 —— UIA 没有昵称，必须靠 OCR 分辨是谁

单聊靠像素只能分「左=对方 / 右=自己」；但群聊左侧可能同时有多个人，必须知道**是谁**。
实测 UIA 树里根本不存在昵称，昵称只能靠 OCR。两条实测规律：

1. 有昵称的行高 **115**，没有昵称的行高 **84** —— 也就是微信在别人的消息上方多画了一行昵称。
2. 昵称固定在行内左上（x≈104, y≈15），正文在其下方（x≈122, y≈61）。

→ **群聊最终方案：UIA 取正文（精确）+ 行高判断有无昵称 + OCR 取昵称 + 像素判左右。**

### 1.3.5 已知的坑

- 微信会同时开好几个同类窗口（主窗口 / 「图片和视频」预览 / 朋友圈 / 设置），而 `EnumWindows` 的返回顺*不保证（实测同机两次就不同）。挑中「图片和视频」预览时就什么都读不到，和"微信改版了 / UIA 坏了"完全分不开。
- 唯一可靠的纯 Win32 判据是标题（主窗口恒为「微信」）：只认标题等于「微信」的那个，分不出来就返回 `None`（宁可不读也不瞎读）。

## 1.4 OCR 链路

最开始我在本机测试时 UIA 是可以拿到内容的，但打包到其他设备、用不同账号测试后发现：微信只把 **2 个后代控件**（`MMUIRenderSubWindowHW` + `Qt51514QWindowIcon`）暴露给UI Automation，于是**什么都读不到**。

而**从实际反馈看：拿不到控件树的是大多数环境，能拿到的只有部分账号 / 机器**。测试起来特别麻烦，我就不跟微信在这件事上纠缠了，直接自己加了 OCR 这条路。

### 1.4.1 能力清单

**能拿到**：

| 信息 | 怎么来的 |
|---|---|
| 当前聊天标题 | 标题栏区域 OCR + 按位图宽度自己检测左边界 |
| 消息正文 | 按**气泡连通域**切出行 → 逐行 OCR |
| 消息类型 | 气泡几何 + 文字与图标：文本 / 图片 / 引用 / **文件** / **链接** / **系统提示**（六类） |
| 发送者左右 | 气泡在行内靠左还是靠右（**和 UIA 共用同一套 `sender.py`**） |
| 群聊昵称 | 行内左上角 OCR（判据见 1.4.4） |
| 时间分隔符 | 居中的灰色小字（"昨天 22:22"那一类） |

**拿不到**：

1. **上下文只有当前一屏**，只能够本地把每屏存下来缝合。
2. **不提供会话列表和输入框内容**（`read_sessions` 返回 `[]`、`read_input_text` 返回 `""`）。
3. **图片 / 表情分不出来**（OCR 只认字）—— 不过它的**气泡分类**反而比 UIA 细：引用块、分享卡片、系统提示都能按形状认出来。

### 1.4.2 性能与优化

| 环节 | 实测 | 怎么做到的 |
|---|---|---|
| 单张 OCR | **0.13 s** | ① `intra_op_num_threads=4`（线程数"自动"在识别模型上要 **233 ms**，显式 4 线程只要 **12 ms**）；② `limit_type: max`（`min` 的语义是"短边 ≥ 736"，会把一条 978×84 的消息行放大成 736×2944，**面积 26 倍**）；③ `use_cls=false` |
| 每拍开销 | **探针 34 ms** + | 探针 = 抓图 + 缩略图哈希、**不做 OCR**，只覆盖「标题栏 + 聊天区」（免得你自己打字就触发一次真读）。 |
| 引擎加载 | 只加载一次（懒建） | 第一次真读时才建引擎，之后常驻；空闲时零 OCR |

### 1.4.3 群聊昵称

| 判据 | 值 |
|---|---|
| 行高 | 有昵称 **115** / 没有昵称 **84** |
| 位置 | 昵称固定在行内**左上**（x≈104, y≈15），正文在其下方（x≈122, y≈61） |
| 确认 | 同一个名字要在**不同的拍里复现两次**才认（OCR 会偶发读错字） |

认不出来的写「**群友**」；**私聊里则绝不出现「群友」**（一个昵称都没认出来 = 没有证据，保持「对方」）。长昵称 / emoji 昵称 / @提及 / 群成员改名片这些样本还不够。

## 1.5 两条链路的取舍

| 维度 | UIA 链路（有控件树的环境） | OCR 链路（拿不到控件树的环境） |
|---|---|---|
| 消息文本 | 精确、零误差 | 可能识别错字 |
| 会话列表（预览/时间） | 结构化 | 不提供 |
| 消息类型 | 靠控件类区分（文本/图片/引用/文件/链接/系统提示） | 靠气泡几何 + 文字与图标，也一样分这六类（**按各自气泡特征分类，比较麻烦**） |
| 抗遮挡 / 后台 | **完全不受影响**，最小化 / 隐藏都能读 | `PrintWindow` 不怕遮挡，**但最小化就抓不到** |
| 发送者左右区分 | 单靠自己拿不到 → 配合同一次抓图的像素 | 气泡像素坐标直接判左右（**同一套 `sender.py`**） |
| 图片消息内文字 | 只有 `[图片]` 占位 | 可识别 |
| 群聊发送者昵称 | 没有 → 也要靠 OCR（见 1.3.4） | OCR 读行内昵称（见 1.4.4） |
| 速度 | 一屏 **50~90 ms** | 探针 **34 ms**；真读 ≈ **380 ms** |
| 选路 | `auto` 自动选；选中后**不来回切** | 同左 |

# 二、内容存储

无论是 UIA 还是 OCR，都只能读取到目前渲染的一屏；为了有更好的上下文效果，在本地存储了
部分聊天记录，数量、时间超过限制直接删除。通过每一屏消息进行拼接，所以"上下文"必须自己攒。

## 2.1 两个库

| 库 | 存什么 | 容量 |
|---|---|---|
| `screens.db`（屏快照） | **上下文的顺序**：每拍把"这一屏长什么样"整体存一条，读取时靠**重叠的消息**把相邻屏缝起来 | 每个会话最近 **40 屏** |
| `history.db`（消息表） | **一条条消息**：口吻样本、AI 被标记过的建议、清空 | 每个会话最近 **500 条** |

- 写屏快照时只存不判断：入库不做新旧判断、不定位置，顺序留到读取时算 —— 这样即使
  用户来回翻、快速滑，也不会因为"写入时的判断错了"而永久丢内容。
- 判不出"在不在底部"时不写：把"往上翻历史"误当成"新消息"，会让库里一秒写进
  一整屏别的窗口的画面（实测踩过）。

## 2.2 去重：

屏快照的去重是跟**最近记录**比，不是只看上一屏：

| 情况 | 动作 |
|---|---|
| 内容签名完全相同（含发送者判定） | **跳过** |
| 文字一样、只有发送者判定变了 | **原地更新**那一屏（不占窗口位） |
| 其它 | 新增一行 |

消息表那边不看滚动位置，改看**重叠点**：拿这一屏跟库里最近 80 条比，找到"最后一条已经在库里的"当重叠点，**只写它之后的**。

## 2.3 拼接：

```
1. 拿最新一屏当底
2. 其余各屏反复尝试往上接：能跟当前序列连续重合的就拼上
   （这一轮拼不上的留着，别的屏拼进来之后它可能就接得上了）
3. 一轮下来谁也拼不上 → 停
4. 折叠重复段 → 5. 跨天切段 → 6. 取最近 N 条
```

- **重合判定**用的是"两屏之间连续的相同消息"，最少 **1 条**就算重合。
- **接不上的屏不硬拼**：隔了很久的两段粘在一起，给模型就是噪音，还挤占上下文额度；这时只保留最新那一段。
- **同一段被拼两遍**（来回滚时可能出现）：判据是"同一段**连续 3 条以上逐字相同**出现两次"，只保留**第一次**那份。

## 2.4 数据处理

1. 垃圾标题不读正文，也不写库。OCR 会把 `X`、`+`、`①` 这种东西读成会话名。

2. 只给"确认过"的会话写库：同一个标题要在不同的拍里出现过两次。OCR 的乱码是偶发的， 下一拍就变了，真会话会一直在。

3. 切会话那一拍要读两次标题：读完正文再读一次，两次指向同一个会话才写。对不上就这一拍不写，下一拍会重读这一屏，只是晚一拍，不丢数据。



- 数据全部在本地（`state/` 下两个 SQLite 文件），程序**不往任何服务器上传**（除了你自己配的 AI 接口，见第三章）。

# 三、提交给智能体

把当前要回复的消息、最近会话的历史消息、我说话的口吻样本、人设等消息整合后丢给智能体。

## 3.1 提示词是怎么拼出来的

```
{人设}                    ← 设置里的「人设」
{关系} + {口吻样本}        ← 设置里全局/会话的关系描述 + 你平时说话的样本
{我想说}                  ← 只在填了的时候拼，且是【最高优先级】
系统提示词                 ← 【硬性禁止】+【上下文规则】（自己可改）
【输出要求】               ← 代码侧，含"生成几条"
【对话历史】               ← 提供上下文，大概知道在聊什么话题
【当前屏幕上的对话】        ← 要回复的就是这一些内容
```

- **「口吻样本」**来自你最近说的话的样本，一起都给智能体学习你是怎么说话的。

- **「我想说」** 直接告诉模型我要说什么，并让他根据语境进行润色。

- 「人设」、「关系」、「系统提示词」都可以在设置自定义编写

  

## 3.2 聊天图片的处理

- 设置里打开**「识别图片」**开关，填**「视觉模型」**。

图片消息本身**不是文字**：UIA 链路只能读到「图片」两个字，图里的内容拿不到；OCR 链路在读整行时会把消息判断为图，部分图可读出里面的字，但只能够大概知道文字在说什么。

所以就是把 `[图片]` 那几条裁出来，直接发给视觉模型，然后综合上下文给出回答。

## 3.3 本地知识库（可选，默认关）

有些话得照着资料回——课程要求、项目约定、产品参数。这些不该让模型凭记忆答，
可以在设置里把资料丢给它：

- 认 **md / txt / pdf / docx**。**一个文件夹就是一个分组**，组名就是文件夹名；
  也可以单独「添加文件」，那些落进「默认」组。分组只影响列表显示，**检索永远在全库做**。
- 资料会被切成小段（每段约 400 字），用本地全文索引检索（中文按二字切分），
  命中后取最相关的 **3 段**、总共不超过 **600 字**，作为【参考资料】拼进提示词。
- 只留"不差于第一名 0.6 倍"的段，太弱的直接扔掉 —— 否则一个虚词就能撞上一堆废段。
- 扫描件 PDF 默认不认（没有文字层，只能走 OCR，约 0.4 秒/页）；有文字层的 PDF 直接抽字。

资料进了提示词之后有一条硬规则（写在代码里、用户改不到）：**只按资料说，资料里没有的别编**；
并且**不要在回复里提"根据资料 / 第几条"** —— 微信里那句话一出口就暴露是机器人。

> 想先看效果：仓库里 `examples/` 就是一套示例资料，命令行跑
> `python tools\kb_try.py --docs examples\kb --queries examples\问法示例.txt`
> 就能看到命中的片段（不装产品、不改配置、不联网）。
